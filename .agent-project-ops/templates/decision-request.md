# 决策请求模板 / Decision request template

> 给 Agent：发给拍板人的每个决定都用这份模板（`PRINCIPLES.md` §12）。只把下面代码块里的内容贴到 GitHub，替换 `{{…}}`，删掉用不上的行；本说明不要贴出去。请求正文按 §13 写：中文、先说结论、少用术语。

## 规则（给 Agent）

1. **什么算正式请求。** Issue/PR 正文或评论的**第一行**是 `<!-- apo-decision v1 | … -->` 标记，才是正式请求。代码块、引用和本模板里的标记都只是示例。
2. **标记字段。**
   - `id`：`D-<n>`，在本仓库内唯一；在 Issue/PR 里搜索 `apo-decision`，取已有最大编号加 1。
   - `rev`：版本号，从 1 开始。
   - `type`：`开工确认`（命中大改动清单 §11，开工前问）、`最终验收`、`例外`（要改已确认的合同）、`发布`（第 4 条）。一次决定几类事用 `+` 连接，例如轻量档的 `最终验收+发布`。
   - `target`：涉及的 Issue/PR，多个用空格分开，例如 `#64 #65`。
   - `disposer`：Command Center 上写明的拍板人。
3. **发在哪里。** 发在目标 Issue/PR 上；涉及多个目标的，发在 Command Center 或当前阶段的 Issue 上。发出后在 Command Center §1“待你决定”里列出，拍板人在同一个讨论里回复。
4. **合并发送。** 同一时间准备好的几个决定合成一个请求，按“决定 1、决定 2……”分节，每节都有推荐和方案对比；回复方式写成 `全部按推荐`，或 `1 批准 A；2 改用 B`。不要一件一件地问。
5. **修改请求。** 发出后要改选项、范围或证据：发一条同 `id`、`rev` 加 1 的新请求，开头一句写明改了什么。旧版本作废，对旧版本的回复不算数，要请拍板人按新版本再回复一次。
6. **哪些回复算数。** 针对最新版本的：`批准 A`、`改用 B`、`退回：<原因>`、`全部按推荐`。只有一个待决请求时，`同意`、`可以`、`按推荐` 视为批准推荐方案；同一讨论里有几个待决请求时，回复要带编号，例如 `D-13 批准 A`。旧决定词照样有效：`FREEZE ACK` = 批准开工确认；`PHASE ACCEPT` / `PHASE RETURN` = 最终验收的批准 / 退回；`EXCEPTION ACCEPT` / `EXCEPTION REJECT` = 例外的批准 / 退回。看不懂的回复追问一次，不要猜。
7. **对话里的回复。** 拍板人在 Agent 对话里回复时，Agent 在同一轮把原话记到 GitHub（见第 8 条），`reply` 写 `对话`。Agent 绝不替拍板人写回复，也不批准自己发的请求。
8. **记录结果。** 收到回复后，Agent 在请求所在的讨论里发“结果记录”（见文末），再到每个 `target` 贴上这条记录的链接——这是引用，不是代签。请求作废或被拍板人撤回时，`result` 写 `撤回`。
9. **只批准写明的内容。** 批准只覆盖请求里写明的范围，不带来任何新权限；超出的部分要另发请求。
10. **等待期间。** 只有被这个请求挡住的工作等待（不改成 `blocked`）；其余任务照常推进。

## 开工确认 / 例外 / 发布

```markdown
<!-- apo-decision v1 | id: D-{{n}} | rev: 1 | type: {{开工确认}} | target: #{{issue}} | disposer: @{{handle}} -->
## 需要你决定：{{一句话说明要决定什么}}

**我的推荐：** 方案 A——{{一句话}}
**为什么需要你：** 命中大改动规则「第 {{N}} 条：{{条目原文}}」
**不决定的影响：** {{哪些工作会一直等着；哪些照常推进}}

### 背景

{{2–4 句白话：现在是什么情况，为什么走到这一步。第一次出现的术语在括号里解释。}}

### 方案对比

| 方案 | 具体做什么 | 好处 | 代价和风险 | 能否撤回 |
| --- | --- | --- | --- | --- |
| A（推荐） | | | | |
| B | | | | |

### 依据

- **影响范围：** {{会改到哪些文件、功能或数据}}
- **证据：** {{链接：PR、CI 运行记录、测试结果、文档}}
- **尚未验证：** {{还不知道或没测过的；没有就写“无”}}

### 回复方式

```
